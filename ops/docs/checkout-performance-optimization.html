Checkout Performance Optimization

Date: 2026-05-13  |  Branch: jbj/local  |  Deployment: Elestio (district11), ghcr.io/mrjbj/hi-events-all-in-one:latest

TL;DR. The lag between clicking Continue on the event homepage and seeing the Order Summary page was reduced from ~352ms typical TTFB to ~117ms steady-state TTFB (3× faster), through a combination of three application-code commits, one Dockerfile/startup fix, one production cache build, and PHP-FPM worker tuning via container env vars. Further optimization requires infrastructure changes (Redis cache, persistent DB connections, geographic CDN) with diminishing returns.

1. The problem

Users on the production Elestio instance reported a noticeable lag after clicking the Continue button on an event homepage. The spinner would appear and the Order Summary page (where the countdown timer starts) took perceptibly long to render. Less noticeable on local dev, more noticeable on the hosted production deployment.

The flow under examination:

  1. User selects tickets on SelectProducts (event homepage product picker)
  2. Clicks Continue
  3. Frontend mutation fires POST /api/events/{id}/order
  4. Backend creates a RESERVED order and returns it
  5. Frontend navigates to /checkout/<eventId>/<orderShortId>/details
  6. CollectInformation page mounts and renders the form

2. Investigation approach

Started with a code-explorer agent tracing the full call chain frontend → backend → database. Then captured production network traces from Chrome DevTools (Network panel, Server-Timing headers) to measure where time was actually spent. Added Server-Timing instrumentation to the backend action so the breakdown was visible per request.

Bottlenecks identified, ranked by user-visible impact

#BottleneckWhere
1Duplicate product-availability SQL (heavy CTE, twice per order)Backend — validation + handler both forced cache bypass
2queryClient.invalidateQueries() awaited before navigationFrontend — blocked navigation behind global cache wipe
33-query waterfall on CollectInformation mount (order → event → questions)Frontend — refetched data that was already known
4Lazy chunks for Checkout layout + CollectInformationFrontend — cold-cache visitors paid 1-2 round trips post-mutation
5Production Laravel caches not built (config, routes, events, views)Backend — startup.sh actively cleared caches
6PHP-FPM default tuning (start=2, min_spare=1, max_requests=0)Container — sparse warm worker pool

3. Changes made

3.1 Backend: cache pre-flight availability check

Commit 96a7094f

The availability check ran twice per order creation — once in OrderCreateRequestValidationService::validateRequestData (pre-flight) and once again inside the advisory lock in CreateOrderHandler::validateProductAvailability. Both forced ignoreCache: true on a heavy multi-join CTE that scans products → product_prices → order_items → orders.

Changed pre-flight to honor the 2-second cache (ignoreCache: false) since the inside-lock recheck remains authoritative and prevents race conditions. The cache hits when the homepage just loaded availability.

backend/app/Services/Domain/Order/OrderCreateRequestValidationService.php:52

// Before
$this->availableProductQuantities = $this->fetchAvailableProductQuantitiesService
    ->getAvailableProductQuantities($event->getId(), ignoreCache: true);

// After
$this->availableProductQuantities = $this->fetchAvailableProductQuantitiesService
    ->getAvailableProductQuantities($event->getId(), ignoreCache: false);

3.2 Frontend: navigate before invalidating queries

Commit 96a7094f

The mutation's onSuccess handler used to await queryClient.invalidateQueries().then(() => navigate(...)). The unfiltered invalidation marked every cached query stale and triggered refetches on any active observers (the homepage's event query) before navigation could proceed.

Changed to navigate immediately and let the invalidation fire-and-forget. Also scoped the invalidation to just the event query (GET_EVENT_PUBLIC_QUERY_KEY) to preserve unrelated caches.

3.3 Frontend: prime order cache before navigation

Commit 96a7094f

The mutation response already contains the full order. Rather than letting CollectInformation mount and fire useGetOrderPublic to refetch the same data, we prime the React Query cache with the mutation result before navigating. Also attach the locally-known event object (from the homepage) so consumers like the Checkout layout that read order.event see complete data immediately.

frontend/src/components/routes/product-widget/SelectProducts/index.tsx

queryClient.setQueryData(
  [GET_ORDER_PUBLIC_QUERY_KEY, eventId, data.data.short_id, null],
  {...data.data, event},
);
navigate(url);
queryClient.invalidateQueries({queryKey: [GET_EVENT_PUBLIC_QUERY_KEY, eventId]});

3.4 Frontend: preload checkout chunks on mount

Commit 1f695603

Both Checkout (layout) and CollectInformation (child route) are lazy-loaded. On cold visits the browser fetched both chunks sequentially after the order POST returned. Added a mount-time useEffect in SelectProducts that fires import() for both, warming the chunks while the user is reading prices.

useEffect(() => {
  if (typeof window === 'undefined') return;
  import("../../../layouts/Checkout");
  import("../CollectInformation");
}, []);

3.5 Backend: Server-Timing instrumentation

Commit 1f695603

Added hrtime() measurements around the three phases of POST /order (validate, handle, serialize) and emitted a Server-Timing response header with Timing-Allow-Origin: *. Browser DevTools → Network → Timing tab now shows the breakdown.

backend/app/Http/Actions/Orders/Public/CreateOrderActionPublic.php

3.6 Container: build caches on startup instead of clearing

Commit c5198551

The all-in-one image's startup.sh was clearing all Laravel caches on every container start, leaving production permanently uncached. Replaced with optimize:clear followed by optimize so caches are wiped (defensive against version drift) then immediately rebuilt fresh from the current code and .env.

docker/all-in-one/scripts/startup.sh

# Before
php artisan cache:clear
php artisan config:clear
php artisan route:clear
php artisan view:clear

# After
php artisan optimize:clear
php artisan optimize

3.7 Container env: PHP-FPM tuning

Set on Elestio via the project .env (consumed by docker-compose)

The serversideup/php base image defaults were too conservative for production:

# PHP worker config — keep workers warm, recycle periodically
PHP_FPM_PM_CONTROL=dynamic
PHP_FPM_PM_START_SERVERS=4
PHP_FPM_PM_MIN_SPARE_SERVERS=2
PHP_FPM_PM_MAX_SPARE_SERVERS=6
PHP_FPM_PM_MAX_CHILDREN=20
PHP_FPM_PM_MAX_REQUESTS=500
Gotcha: docker-compose's .env only does variable substitution in docker-compose.yml by default. To actually pass these to the container, the compose file must either reference each var in an environment: block or include env_file: .env on the service.
Gotcha 2: Inline # comments after a value (e.g. VAR=value # note) are not stripped by docker-compose's .env parser — the entire string after = becomes the value. Always put comments on their own line.

5. Production configuration

Required env vars (Elestio .env on the host)

# PHP worker config — keep workers warm, recycle periodically
PHP_FPM_PM_CONTROL=dynamic
PHP_FPM_PM_START_SERVERS=4
PHP_FPM_PM_MIN_SPARE_SERVERS=2
PHP_FPM_PM_MAX_SPARE_SERVERS=6
PHP_FPM_PM_MAX_CHILDREN=20
PHP_FPM_PM_MAX_REQUESTS=500

# Turnstile bot protection (already enabled before this work)
TURNSTILE_ENABLED=true
VITE_TURNSTILE_SITE_KEY=...
TURNSTILE_SECRET_KEY=...

docker-compose.yml requirement

The compose file for the Hi.Events service on Elestio must either include env_file: .env on the all-in-one service, or list each PHP_FPM_* var in an environment: block. Without this, the .env file is read but not propagated into the container's environment.

What ships in the image (via this fork)

  • startup.sh runs php artisan optimize on every container start (commit c5198551)
  • Server-Timing header on POST /order for diagnostics (commit 1f695603)
  • All frontend optimizations: cache priming, scoped invalidation, chunk preload (commits 96a7094f, 1f695603)
  • Backend pre-flight availability uses cache (commit 96a7094f)

6. Things considered and rejected

Backend B — pass loaded $event / $account into OrderItemProcessingService

Would eliminate 1–4 small queries inside the advisory lock (redundant event + account fetches, plus N+1 product loop). Realistic savings: 15–60 ms inside the lock.

Rejected because: the handle phase is already only ~42 ms. Saving 15 ms there is below user perception threshold. The refactor cost (modifying signatures, updating tests) outweighed the benefit.

Adding Redis to the stack

Would speed up Laravel's cache driver (currently file) and session driver. The 2-second product availability cache could become a hot Redis hit instead of disk I/O.

Rejected because: the file cache is on a fast volume and isn't currently the bottleneck (Server-Timing shows validate is only ~17 ms even with file cache). Adding Redis is a meaningful infra change (new container, new env vars, new monitoring surface) for marginal latency win.

Persistent Postgres connections

Laravel's default opens a fresh Postgres TCP connection per request. Switching to persistent connections would shave the TCP handshake from every request (5–50 ms variable).

Deferred: would help with the occasional gap spike but has tradeoffs (connection limit exhaustion, stale connection issues). Worth revisiting if real-user spike reports appear.

Removing Cloudflare Turnstile

Turnstile loads a 364 KB script per page and triggers a 401 challenge handshake. Looks heavy in the network panel.

Rejected: the bot protection is genuinely valuable for a ticketing platform (scalper bots, fake orders). The implementation is well-engineered (14-minute freshness cache, invisible mode, lazy script load) and the cost is amortized across user reading time, not blocking Continue clicks. The 401 errors are normal Turnstile protocol, not real failures.

Geographic CDN / closer hosting

Network RTT to Elestio's data center accounts for some of the irreducible gap. Hosting closer to users would help.

Deferred: beyond scope for an in-flight perf pass. Worth considering if Hi.Events instance grows internationally.

7. How to verify it's still working

Check Laravel caches are built

ssh root@district11 \
  'docker exec -w /app/backend hi-events-all-in-one-1 php artisan about --only=cache'

Expected: all four rows (Config, Events, Routes, Views) show CACHED.

Check PHP-FPM tuning is applied

ssh root@district11 'docker exec hi-events-all-in-one-1 env | grep PHP_FPM_PM'

Expected values:

PHP_FPM_PM_CONTROL=dynamic
PHP_FPM_PM_START_SERVERS=4
PHP_FPM_PM_MIN_SPARE_SERVERS=2
PHP_FPM_PM_MAX_SPARE_SERVERS=6
PHP_FPM_PM_MAX_CHILDREN=20
PHP_FPM_PM_MAX_REQUESTS=500

Check PHP-FPM actually honored them (vs being set but ignored)

ssh root@district11 \
  'docker exec hi-events-all-in-one-1 php-fpm -tt 2>&1 | grep -E "^\[.*pm[ \.]"'

Look for pm = dynamic, pm.start_servers = 4, etc.

Measure POST /order TTFB

Open the production site → DevTools Network panel → click Continue → click the order row (status 201) → Timing tab. Look at:

  • Waiting for server response (TTFB) — should be 100–150 ms typical
  • Server Timing → total — should be 50–80 ms
  • Gap (TTFB minus total) — should be 50–100 ms typical, occasional spikes acceptable

8. Future considerations

If users start reporting slowness again

  1. Pull a fresh network trace with Server-Timing — check if it's total growing (server work) or the gap growing (infra)
  2. Run php artisan about --only=cache — confirm caches still built; redeploys with the new startup.sh should keep this state, but verify
  3. Check Postgres slow query log for any new queries that crept in
  4. Check Cloudflare analytics for edge latency anomalies

If load grows significantly

  1. Add Redis to the stack and switch CACHE_DRIVER=redis, SESSION_DRIVER=redis
  2. Switch QUEUE_CONNECTION from sync to database or redis — sync queue blocks responses on dispatched jobs (currently no jobs dispatch during order creation, but other flows do)
  3. Consider Postgres persistent connections (config/database.php → 'options' => [PDO::ATTR_PERSISTENT => true])
  4. Bump PHP_FPM_PM_MAX_CHILDREN based on observed memory headroom

Upstream PR considerations

The frontend and backend code changes (commits 96a7094f and 1f695603) are general improvements that benefit any Hi.Events deployment and would likely be welcomed upstream. The startup.sh change (commit c5198551) is more opinionated — upstream may prefer the clear-on-restart behavior for the typical self-hosted user. If submitting, frame it as a HIEVENTS_OPTIMIZE_ON_START=true opt-in flag rather than changing the default.
